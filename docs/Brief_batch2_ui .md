# BRIEF الدفعة الثانية: الواجهة الحية + تشغيل مستقل على ويندوز

متابعة لمشروع RMS Rover v2. الدفعة الأولى للملاحة اكتملت (`pi/nav/` — 18/18 اختبار ناجح، منطق خالص). المطلوب الآن: **ربط هذه الوحدات بسيرفر وواجهة ويب** تعرض المسح بصرياً في وضع المحاكاة.

**شرط أساسي جديد: كل شيء في هذه الدفعة يجب أن يعمل على ويندوز بلا راسبري وبلا أي عتاد.** الراسبري مطفأ، والتطوير يجري على اللابتوب، والمزامنة عبر git.

---

## أ) التوافق مع ويندوز — قبل أي شيء آخر

المشكلة: مكتبات العتاد (`lgpio`, `adafruit-circuitpython-bno055`, وغيرها) **لا تُثبَّت ولا تعمل على ويندوز**. أي استيراد لها عند تحميل الوحدة سيكسر التشغيل.

**المطلوب:**

1. **لا استيراد عتاد على مستوى الوحدة إطلاقاً.** كل استيراد لمكتبة عتاد يكون داخل دالة أو خلف `try/except ImportError` مع بديل محاكاة:
   ```python
   HARDWARE_AVAILABLE = False
   try:
       import lgpio
       HARDWARE_AVAILABLE = True
   except ImportError:
       pass   # ويندوز/بيئة تطوير — سنستخدم المحاكاة
   ```
2. **كشف المنصة تلقائياً**: عند غياب مكتبات العتاد، يُجبَر `SIMULATION_MODE=True` وتظهر لافتة واضحة في الواجهة: "وضع المحاكاة — لا يوجد عتاد متصل". لا فشل صامت ولا رسائل خطأ مبهمة.
3. **فصل المتطلبات**:
   - `requirements.txt` — للراسبري (يشمل lgpio, adafruit, opencv...).
   - `requirements-dev.txt` — للتطوير على ويندوز/ماك: fastapi, uvicorn, websockets, numpy فقط. **بلا أي مكتبة عتاد.**
4. **المسارات**: استخدم `pathlib` لا سلاسل مسارات بشرطة مائلة، حتى تعمل على ويندوز ولينكس معاً.
5. **أضف في README قسم "التشغيل على ويندوز"** بأوامر PowerShell كاملة (إنشاء بيئة افتراضية، تثبيت requirements-dev، تشغيل السيرفر، فتح المتصفح).

**معيار حاسم**: `git clone` على ويندوز نظيف + `pip install -r requirements-dev.txt` + أمر تشغيل واحد = واجهة تعمل بالكامل في المتصفح. بلا راسبري، بلا عتاد، بلا تعديل يدوي.

## ب) السيرفر — `pi/web/server.py`

- FastAPI + WebSocket على المنفذ 8000 (`http://localhost:8000` على ويندوز).
- يستورد وحدات `pi/nav/` (منطق خالص، تعمل على ويندوز أصلاً) ويقودها بمحرك `sim_world.py`.
- **حلقة محاكاة زمنية**: خطوة كل فترة قصيرة (قابلة للضبط)، مع **مضاعف سرعة** (×1، ×5، ×20) حتى لا تنتظر مسح غرفة كاملة بالزمن الحقيقي — مهم جداً للتجربة والعرض.
- بث WebSocket كل ~200ms: موقع الروبوت، heading، نصف قطر عدم اليقين، الخلية الحالية، حالة الشبكة (المتغيّرة فقط لتوفير النطاق)، المسار المخطط، القراءة الحية، حالة المهمة، التغطية.
- REST: إعداد الغرفة، المعايرة، بدء/إيقاف/استئناف، تنزيل CSV والتقرير، وضع العوائق الوهمية.

## ج) الواجهة — ما يجب أن يُرى

ثيم داكن، عربية RTL للنصوص، بلا أي CDN (self-contained).

1. **نموذج إعداد الغرفة**: طول × عرض بالمتر، ركن الانطلاق (4 أزرار)، تباعد المسح، اختيار ملف المعايرة من قائمة (وزر "معايرة جديدة" — في المحاكاة تُملأ بقيم افتراضية مع وسم "محاكاة").
2. **خريطة الشبكة الحية** (canvas خفيف، هي جوهر الواجهة):
   - خلايا ملونة: غير مزارة (رمادي باهت)، مزارة (بلون مستوى الخطر الخمسة)، محجوبة (نمط مائل)، غير قابلة للوصول (لون مميز)، ذات أولوية (إطار بارز).
   - الروبوت: مثلث يشير لاتجاه heading + **دائرة عدم اليقين** شفافة حوله.
   - **المسار**: المسار المخطط (خط باهت) والمسار المقطوع فعلياً (خط واضح) — وعند إعادة التخطيط يتغير المسار البالت أمام عينك.
   - علامة على الخلايا التي سُجّل فيها شذوذ.
3. **لوحة الحالة**: التغطية بالرقمين (نسبة + عدد قابل للوصول/محجوب)، الموقع (x,y)، heading، نصف قطر عدم اليقين، عدد التصحيحات المطبقة، القراءة الحالية µSv/h ومستوى الخطر، زمن المهمة.
4. **أزرار التحكم**: بدء مسح، إيقاف مؤقت، استئناف، إيقاف طوارئ (بارز)، عودة لنقطة الانطلاق، مضاعف السرعة، **وأداة اختبار: النقر على خلية في الخريطة يضع/يزيل عائقاً وهمياً** — لتجرب إعادة التخطيط بنفسك مباشرة وترى المسار البديل يُرسم.
5. **رسم زمني** بسيط لـCPM آخر دقائق.
6. **سجل أحداث** جانبي: بدء، تصحيح جدار مطبَّق، عائق مكتشف، إعادة تخطيط، شذوذ، انتهاء.
