# PATCH: مصدر الاتجاه خلف واجهة واحدة + إعادة المعايرة مع BNO055

**السبب**: جايرو الروفر الداخلي (`gz` من `T=126`) **مات** — I2C الداخلي معطّل.
كان تكامل الجايرو مكتوباً داخل `WaveRoverBridge` مباشرة، فتبديل الحسّاس يعني
تعديل جسر الروفر. وكل معايرة اتجاه سابقة **باطلة** لأنها أُخذت عبر الحسّاس الميت
بمعدل قراءة مختلف (~120ms مقابل ~50ms لـBNO055).

---

## 1) ما تغيّر في الشيفرة

| ملف | التغيير |
|---|---|
| `pi/sensors/heading.py` **(جديد)** | الواجهة الواحدة: `HeadingSource` + 4 مصادر + `RateConditioner` + `robust_bias` + `make_heading_source` |
| `pi/nav/heading_hold.py` **(جديد)** | متحكم PD لتثبيت الاتجاه (منطق خالص): `HeadingController` + `available_headroom` + `config_sanity` |
| `pi/sensors/imu.py` | `gyro_z_dps()` و`euler_yaw()`، وضع **IMUPLUS**، قُفل I2C، قارئ مشترك `get_imu()` |
| `pi/rover/bridge.py` | لا معادلة تكامل: `heading`/`gyro_bias` صارت **خصائص** تقرأ من المصدر؛ حارس **الإشارة المقلوبة**؛ `robust_bias` مُعاد تصديره للتوافق |
| `pi/nav/executor.py` | لفّة أُجهضت (`aborted`) = فشل صريح لا نجاح |
| `pi/nav/mission.py` | **الحدّ الزمني** بديلاً عن حماية الجهد المعطّلة + بثّ حالة مصدر الاتجاه |
| `pi/web/server.py` | القارئ المشترك + بثّ `imu_mode`/`mag_used`/`gyro_z_dps`/`heading_source` |
| `pi/tests/calibrate_heading.py` **(جديد)** | سكربت المعايرة على العتاد (3 مراحل) |
| `pi/nav/selftest.py` | 34 اختباراً جديداً (المجموع **86/86**) |

### المصادر الأربعة (`HEADING_SOURCE`)

| القيمة | الحسّاس | الحساب | الحالة |
|---|---|---|---|
| `bno055_gyro` | BNO055 `gyro.z` عبر I2C | `h += (gz−bias)·dt·scale` | **الافتراضي** |
| `bno055_fusion` | BNO055 yaw (IMUPLUS) | فرق زاوية ملفوف | بديل للمقارنة |
| `rover_gyro` | `T=126 gz` | تكامل | **الحسّاس ميت** — توثيق/تراجع |
| `sim` | جسر المحاكاة | تكامل | ويندوز/بلا عتاد |

التبديل بلا لمس كود: `RMS_HEADING_SOURCE=bno055_fusion python3 -m pi.web.server`

### ثلاثة أخطاء صامتة أُغلقت

1. **حسّاس ميت يبدو سليماً**: قراءة `0.0` مضبوطة متتابعة (40 مرة) تُعلن
   `ok=False` بسبب مقروء. الجايرو الحيّ لا يعطي صفراً مضبوطاً أبداً — وهذا
   بالضبط ما جعل الجايرو الميت يمرّ بلا إنذار.
2. **إشارة محور z مقلوبة**: تعتمد اتجاه تثبيت الحسّاس. لو دار الروبوت عكس
   المطلوب > 15° يُجهض اللفّ فوراً برسالة تشير إلى `BNO055_GYRO_Z_SIGN`،
   بدل الدوران حتى المهلة.
3. **سقف تصحيح لا يُطبَّق**: سكربت العتاد `docs/ff.py` استخدم `MAX_CORR=0.25`
   مع أساس قوة 0.35 → 0.628 > حدّ 0.5، فالزائد كان يُقصّ صامتاً. الآن السقف
   **مشتق**: `base + |trim| + corr ≤ MAX_MOTOR_POWER` (0.35+0.028+0.12=0.498).

## 2) القيم في config — ما هو مقاس وما هو تقديري

| ثابت | القيمة | الحالة |
|---|---|---|
| `BNO055_GYRO_SCALE` | `1.000` | ⚠ **غير معاير** — المرحلة 2 |
| `HEADING_KP` | `0.015` | ⚠ تقديري: 0.035 (ff.py @120ms) × 50/120 — المرحلة 3 |
| `HEADING_KD` | `0.004` | ⚠ تقديري (المشتقّة أضجّ عند معدل أسرع) |
| `HEADING_MAX_CORR` | `0.12` | **مشتق** من حدّ القوة (لا يُخمَّن) |
| `HEADING_DEADBAND_DPS` | `1.5` | ⚠ تقديري من ضجيج الحسّاس الميت — المرحلة 1 |
| `MOTOR_TRIM_L/R` | `+0.028 / −0.028` | مقاس على السيراميك (ff.py) |
| `STRAIGHT_BASE_POWER` | `0.35` | مقاس (ff.py) |
| `GYRO_SCALE` (روفر) | `0.9275` | **باطل** — للتوثيق فقط |
| `MISSION_TIME_LIMIT_S` / `HARD` | `480` / `600` | ⚠ تقديري — القسم 9 |

## 3) إجراء المعايرة على العتاد (بالترتيب)

```bash
cd ~/RMS-Rover-v2 && source venv/bin/activate
i2cdetect -y 1                      # يجب أن يظهر 29
```

### المرحلة 1 — الانحياز والضجيج (بلا حركة، دقيقة)

```bash
python3 -m pi.tests.calibrate_heading --stage 1 --seconds 10
```

الروبوت **ساكن على سطح ثابت**. المخرَج: معدل القراءة الفعلي (تحقّق من ~50ms)،
الانحياز، σ، و`HEADING_DEADBAND_DPS = 3σ` مقترحة.

- انحياز > 20°/ث والروبوت ساكن ⇒ خطأ وحدات أو اهتزاز → راجع `BNO055_GYRO_IN_RAD`.
- ضع القيمة المقترحة في config قبل المرحلة 2 (العتبة تؤثر في التكامل).

### المرحلة 2 — `BNO055_GYRO_SCALE` (لفّات، ~5 دقائق)

```bash
RMS_ROVER_MODE=real python3 -m pi.tests.calibrate_heading --stage 2 --angle 180 --trials 3
```

1. علّم اتجاه مقدّمة الروبوت على الأرض بشريط لاصق.
2. Enter → يلفّ 180°.
3. علّم الاتجاه الجديد، قِس الزاوية بمنقلة، أدخِلها (موجبة إن دار بالاتجاه المطلوب).

اللفّة الكبيرة أدق (خطأ العين النسبي أصغر). المخرَج: وسيط ثلاث لفّات + تشتتها،
ومقارنة مع `bno055_fusion` — **الأقرب إلى 1.0 هو المصدر الأصدق** فاعتمده في
`HEADING_SOURCE`.

- إن ظهر `⛔ sign_mismatch` ⇒ `BNO055_GYRO_Z_SIGN = -1` وأعِد المرحلة.
- معامل ≈57 أو ≈0.017 ⇒ خطأ وحدات لا معايرة.
- تشتت > 0.10 ⇒ انزلاق عجلات أو قياس غير دقيق: أعِد التجارب.

### المرحلة 3 — `HEADING_KP` و`HEADING_MAX_CORR` (ممر ≥3م، ~10 دقائق)

```bash
RMS_ROVER_MODE=real python3 -m pi.tests.calibrate_heading --stage 3 --duration 4 \
    --kp 0.008,0.015,0.025,0.035
```

لكل مرشّح KP شوط سير مستقيم، ويُقاس: الخطأ (متوسط/أقصى/نهائي)، **التذبذب**
(تبديل إشارة التصحيح)، نسبة الإشباع، ومعدل الحلقة. بعد كل شوط قِس الانحراف
الجانبي بالسنتيمتر وأدخِله (يُحفظ كدليل).

- الترتيب: `score = متوسط الخطأ + 2×(تذبذب/ثانية)` — التذبذب يُعاقَب لأنه يزيد
  انزلاق العجلات فيفسد حساب المسافة في `deadreckoning`.
- `MAX_CORR` المقترح = مئين 95 للتصحيح × 1.5، مقصوصاً على الفراغ المتاح.
- إشباع > 20% ⇒ أنزِل `STRAIGHT_BASE_POWER` ليتّسع الفراغ، أو خفّض KP.

النتائج الخام تُحفظ في `docs/results/heading_calibration_<ts>.json`، وأسطر config
تُطبع للّصق — **السكربت لا يعدّل config تلقائياً**. سجّل مع كل قيمة: التاريخ،
الأرضية، وحالة البطارية.

## 4) القسم 9 — الحدّ الزمني بديلاً عن حماية الجهد

مراقبة الجهد معطّلة (`BATTERY_MONITOR_ENABLED = False`)، وترك المهمة بلا حماية
استنزاف مرفوض (سُجّل هبوط إلى 8.98V قبل الحماية). البديل زمني من **بدء المهمة**
بزمن الحائط:

| الزمن | الإجراء |
|---|---|
| 300ث | تنبيه في السجل |
| 480ث | **عودة إجبارية (RTH)** |
| 600ث | **إيقاف محركات فوري** |

الجهد يُعرض «غير معروف» لا تصنيفاً أخضر كاذباً. أعِد `BATTERY_MONITOR_ENABLED`
إلى `True` لحظة عودة قراءة الجهد — الحماية الجهدية أدقّ، والزمن حاجز خام لا يعرف
حالة الشحن الابتدائية، **فابدأ كل مهمة ببطارية مشحونة**، واضبط الرقمين على أول
علامة ضعف مقاسة (تباطؤ محرك / لفّة ناقصة).
